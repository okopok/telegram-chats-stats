# Архитектура chatStats

Личный PHP CLI-инструмент: парсит HTML-экспорты чатов Telegram Desktop и генерирует по одной статической HTML-странице статистики на чат. Без фреймворка, веб-сервера, тестов, CI и линтера.

## Пайплайн (поток данных)

```
bin/chatstats
  → Application                      — сборка CLI-приложения (symfony/console, имя «chatstats»)
  → Console/GenerateCommand          — команда generate: опции, реестр обработчиков, кэш результатов, рендер
  → MessageSource                    — интерфейс: getMessages()
      ├─ ExportMessageSource         — парсинг HTML-файлов экспорта (генератор, потоково)
      └─ CachedMessageSource         — кэш сообщений чанками поверх ExportMessageSource
  → MessageCollection                — ленивый однопроходный агрегатор всех статистик
  → Engine                           — последовательно выполняет обработчики Stats\StatHandler
  → ResultsCache                     — кэш результата Engine::calculate()
  → Renderer/HtmlRenderer            — рендер index.twig (Twig)
  → var/html/<key>.html              — готовая статическая страница
```

## Слои и ключевые классы

### `src/Messages/` — источники сообщений

- **`MessageSource.php`** — интерфейс: `getMessages()` (генератор сообщений).
- **`ExportMessageSource.php`** — читает все файлы папки экспорта (сортировка `natsort`, подпапки и `.DS_Store` пропускаются), парсит через symfony/dom-crawler по CSS-селекторам. Типы медиа определяются декларативной картой `MEDIA_SELECTORS` (порядок в карте = приоритет). Парсер поддерживает **два поколения разметки** экспорта Telegram Desktop: новую (2025+) — фото/стикеры/гифки/видео вне `div.media_wrap` (`a.photo_wrap`, `a.sticker_wrap`, `a.animated_wrap`, `a.video_file_wrap`), документы `.media_file`, локации `.media_location`, `media_video` с title «GIF»/«Video»; и старую — всё внутри `div.media_wrap`, photo/sticker по `title` в `div.media_photo`, документы `.media_document`, локации `.media_live_location`. Даты в `title` парсятся через `DateHelper::parseExportedDate()` (поддерживает и русский «11 декабря 2022, 22:51:24», и английский форматы). **`getMessages()` — генератор**: сообщения отдаются потоково, вся коллекция в памяти не собирается. Конструктор принимает необязательный `$limit` — обрабатываются только первые N сообщений (быстрые проверки). Возвращает сообщения **только с `reply_to_id`**. Помимо медиа парсятся атрибуты: реакции (`div.reactions > span.reaction`: эмодзи + количество), пометка `edited` (текст блока даты), источник пересылки (`div.forwarded_from`), сайт/заголовок веб-превью (`a.webpage_preview`), а также детали медиа — имя и размер документа (`div.media_file`), длительность голосового (`div.media_voice_message .status`) и видео (`div.video_duration`), вопрос и варианты опроса (`div.media_poll`).
- **`CachedMessageSource.php`** — пишет сообщения **чанками по 5000** нативным `serialize` в `var/cache/parsers/<signature>-v3/<NNNNN>.ser` (память на запись = один чанк, а не вся коллекция). Ключ кэша — **сигнатура содержимого папки** (имена файлов + mtime): любое изменение экспорта автоматически пересобирает кэш. Суффикс `-v3` — **версия формата кэша**: при изменении сериализуемых сущностей (новые поля) версия поднимается, и старый кэш без новых данных считается невалидным. `reply_to_message` намеренно не сериализуется (реплики агрегируются отдельным проходом), поэтому кэш не раздувается рекурсией. Уважает флаги `--no-cache` (не читать и не писать) и `--rebuild` (пересобрать принудительно).
- **`MessageCollection.php`** — ленивый однопроходный агрегатор: источники — коллекция (`--no-cache`) или чанки кэша (`iterate()`). Первое обращение к любому методу агрегации выполняет один проход по всем сообщениям и наполняет кэш всех панелей. Агрегации: `count()`, `firstByDate()`, `usernames()`, `countByUser()`, `strlenByUser()`, `medianStrlenByUser()`, `strlenTotal()`, `countByDate($format)`, `medianByDate($format)`, `countByUserDayHour()`, `activityHeatmap()`, `countByType()`, `countByTypeAndUser()`, `repliesMatrix()`, `reactionTotals()`, `reactionByUser()`, `reactionRecvByUser()`, `reactionByType()`, `topReactedMessages()`, `editedByUser()`, `forwardedByUser()`, `forwardedSources()`, `sitesByUser()`, `mediaWeight()`, `pollsStats()`, `replySpeed()`, `chronotypes()`, `longestStreak()`, `userStreaks()`, `lastActivity()`, `selfReplies()`, `longestMessages()`. `firstByDate` — однопроходный поиск минимума (без `sortBy`, который копировал всю коллекцию). Матрица реплаев считается вторым проходом по целям (`reply_to_id` → юзер), без хранения всех сообщений; в том же втором проходе считаются само-ответы (`selfReplies`) и даты целей для скорости ответа (`replySpeed`). Топ-N (реакции, длинные сообщения) держится в памяти ограниченным (срез до 20/10).

### `src/Stats/` — обработчики статистики

- **`StatHandler.php`** — интерфейс: `key()`, `description()` (по-русски), `template()`, `handle(MessageCollection): array`.
- **`AbstractStatHandler.php`** — база для типовых обработчиков.
- **13 обработчиков** — чистые функции без состояния, возвращают массивы-контракты для шаблонов. Полный список и порядок регистрации — в [разделе «Разработка»](development.md#реестр-обработчиков). Сейчас их **27**: базовые 13 + новые панели (реакции, контент-хиты, правки, пересылки, сайты, медиа-вес, опросы, скорость ответа, хронотипы, тепловая карта, серии, активность, само-ответы, длинные сообщения).
- **`Words/WordsAnalyzer.php`** — подсчёт популярных слов (`mb_ereg`/`mb_split`, без внешних стринг-библиотек) на обычных PHP-массивах (без Illuminate Collections): заметно меньше памяти. Итерирует сообщения через `MessageCollection::iterate()` потоково.

### Остальное

- **`src/Engine.php`** — последовательно вызывает `handle()` каждого обработчика в порядке регистрации; при `--debug` замеряет каждый обработчик через symfony/stopwatch.
- **`src/ResultsCache.php`** — кэш результата `Engine::calculate()`: `key => data` сериализуется в `var/cache/results/<sig>.ser`. Сигнатура = сигнатура экспорта + mtime всех файлов `src/` и `config/` — изменение кода инвалидирует кэш автоматически. Повторный прогон не десериализует сообщения и не выполняет обработчики (память ~20MB вместо ~2.5G на больших чатах).
- **`src/Renderer/HtmlRenderer.php`** — рендер `index.twig` + запись результирующего файла.
- **`src/Entity/`** — простые DTO с публичными свойствами: `Message`, `User`, типы медиа (`Photo`, `Sticker`, `Video`, `Voice`, `Document`, `Animation`, `Audio`, `Contact`, `Location`, `Poll`), реакция `Reaction` (не `MessageType`), маркерный интерфейс `MessageType`. Наличие медиа определяется по непустым полям. `Message` несёт атрибуты: `reactions` (массив `Reaction`), `edited`, `forwarded_from`, `webpage_site`, `webpage_title`; у медиа есть детали: `Document::name/size_kb`, `Voice::duration_sec`, `Video::duration_sec`, `Poll::question/answers`. JMS-сериализатор не используется (кэш — нативный serialize).
- **`src/UserHelper.php`** — `norm($username, $namesMap)`: срезает ` via @channel` и применяет карту имён из `config/users.php`.
- **`src/DateHelper.php`** — утилиты работы с датами: `parseExportedDate()` (`title`-дата экспорта → timestamp, включая русские названия месяцев), `getDayName()`, `getMonthName()`.
- **`src/Application.php`** — сборка CLI-приложения.

## Память и кэши

Главный принцип: **сообщения не живут в памяти целиком** — только один чанк (5000 сообщений) за раз. Пик памяти не зависит от размера чата.

- **Кэш сообщений**: `var/cache/parsers/<signature>-v3/<NNNNN>.ser` (нативный serialize, чанки по 5000). Сигнатура = имена файлов + mtime папки экспорта → любое изменение экспорта инвалидирует кэш автоматически; суффикс `-v3` — версия формата, меняется при изменении сущностей (иначе старый кэш без новых полей считался бы валидным).
- **Кэш результатов**: `var/cache/results/<sig>.ser` — результат всех 27 обработчиков. Сигнатура = сигнатура экспорта + mtime всех файлов `src/` и `config/` (изменение кода/конфигов инвалидирует). Повторные прогоны читают только этот кэш.
- При `--limit=<N>` сигнатура получает суффикс `-limit-N` (у обоих кэшей): проверочные прогоны не пересекаются с полными.
- `reply_to_message` не сериализуется — реплики агрегируются вторым проходом.
- `--no-cache` — не читать и не писать кэши; `--rebuild` — пересобрать кэш сообщений принудительно.
- При `--debug` кэш результатов не используется (нужны честные тайминги обработчиков).
- `bin/chatstats` поднимает `memory_limit` до 2G: стартовый полный прогон чата на ~1M сообщений (до кэша результатов) требует до ~350MB, но запас нужен на пиковые моменты сериализации.
- **Топ-N в агрегатах** (`topReactedMessages`, `longestMessages`) хранится ограниченно (срезы 20/10) — топ сообщений не держит весь чат в памяти.

## Режим отладки (`--debug`)

- Таблица таймингов обработчиков (Stopwatch): событие, время в секундах, память в Кб.
- Twig настраивается с `auto_reload => !$debug` — инвертировано **намеренно**: в обычном режиме шаблоны перезагружаются всегда (страницы генерируются редкими запусками, а не «на лету»), при `--debug` — используется кэш `var/twig/cache`.
- Глобалы Twig: `nicksEnabled`, `nicksMap` (заполняются при `--nicks`). Фильтры отображения имён: `user_link` (HTML-ссылка на профиль) и `nicks` (ники для canvas-графиков, где ссылки невозможны). Фильтр `duration` — секунды → «1 мин 23 с».

## Дашборд и «забавные факты»

`GenerateCommand::buildDashboard($results)` собирает из готовых результатов обработчиков KPI-карточки (всего сообщений, участников, дней чата, медиа, реакций, знаков, сообщений/день) и карточки-фанфакты (самое длинное сообщение, рекордная серия дней, пиковый час, объём голосовых, топ-сайт и т.д.). Повторных проходов по сообщениям нет; данные попадают в `index.twig` через `HtmlRenderer::render(..., $dashboard)`.

## Структура выходных данных

`GenerateCommand` собирает результат каждого обработчика в массив `key => {description, data, template}` и передаёт его рендереру; порядок панелей на странице = порядок регистрации обработчиков.
